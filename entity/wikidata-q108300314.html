Who It Is

In C, rint looks deceptively simple — give it 2.3, get back 2.0 — but it is the one rounding function that actually listens. Unlike round(), which always marches away from zero, rint() obeys the floating-point environment's current rounding direction and, when it has to nudge a value, politely raises the inexact flag to tell you it did so. That obedience made it essential to IEEE 754, controversial to standardize, and easy to misuse for 25 years.

Deterministic and stateful: rint's result depends on global floating-point state (the rounding direction set by fesetround() and queried by fegetround()). Under default FE_TONEAREST (round to nearest, ties to even), it behaves like bankers' rounding. Under FE_TOWARDZERO it truncates, under FE_UPWARD it ceils, under FE_DOWNWARD it floors. Second behavior: exception signaling. If the rounded result differs from the argument, rint may raise FE_INEXACT (and on some implementations FE_INVALID is never raised). This contrasts with nearbyint(), which is required NOT to raise FE_INEXACT.

Name & Tongue

Etymology — Clipped from English 'round to integer' or 'round integer'. Attested in 4.3BSD math library (1986) and Sun FDLIBM as rint(); the name was retained verbatim when adopted into ISO/IEC 9899:1999. The f and l suffixes follow the C99 convention: f for float, l for long double (ISO/IEC 9899:1999 §7.12).

Pronunciation — /rɪnt/ — pronounced as the English word 'rint', rhyming with 'print' without the p; commonly spelled out as R-I-N-T in committee discussion. No official IPA in standard.

Aliases — rintf, rintl, rint(), RINT

Ownership — Public domain technical artifact. Originated in Unix/BSD numerical community (UC Berkeley, Sun Microsystems) and standardized by ISO/IEC JTC1/SC22/WG14 (C committee) with IEEE 754

Powers
Round to integral using current rounding mode

Returns the nearest integral floating-point value to x according to the active rounding direction (FE_TONEAREST, FE_DOWNWARD, FE_UPWARD, FE_TOWARDZERO). Ties resolved per mode; under FE_TONEAREST ties go to even mantissa.

Limit: Result is still floating-point; may overflow to infinity if x is huge and rounding mode pushes outward (rare). For |x| >= 2^(mantissa bits), x is already integral in its format and is returned unchanged. Does not convert to integer type.

Inexact exception signaling (may raise FE_INEXACT)

If the return value differs from x (i.e., fractional part discarded), rint is permitted (and on IEEE 754-conforming implementations, required) to raise the floating-point exception FE_INEXACT, detectable via fetestexcept(FE_INEXACT) or fenv state.

Limit: C standard says 'may raise' — not 'shall' — to allow non-IEC 60559 implementations. nearbyint() is the variant guaranteed NOT to raise. Program cannot rely on errno.

Type-generic dispatch via <tgmath.h>

Macro rint(X) in <tgmath.h> selects rintf, rint, or rintl at compile time based on argument type (float/double/long double). In C++ <cmath>, overloading provides same.

Limit: tgmath.h macro only works for real types; complex types not applicable. Requires including <tgmath.h> explicitly in C; C++ does not provide <tgmath.h>.

Preservation of NaN/Infinity payloads

If x is NaN, returns NaN (quieted per IEEE 754); if ±Inf, returns ±Inf; if ±0, returns ±0 with same sign. No exception except possibly FE_INVALID for signaling NaN.

Limit: Signaling NaN handling implementation-defined; may raise FE_INVALID before returning quiet NaN.

Related integer conversion siblings (lrint, llrint)

Not powers of rint itself, but rint family includes lrint/llrint which do convert: long int lrint(double x) and long long llrint(double x) round using current mode and convert, raising FE_INVALID on overflow. Often confused as same function.

Limit: Overflow undefined/out-of-range raises FE_INVALID and returns unspecified value; not safe without range check.

Form & Signs

Symbols — Associated symbols: <math.h>/<cmath> inclusion guard, libm linkage flag -lm, floating-point environment macros FE_TONEAREST, FE_TOWARDZERO, FE_UPWARD, FE_DOWNWARD from <fenv.h>, exception flag FE_INEXACT. In man pages and cppreference, represented by formula '⌊x⌉_mode' or 'round(x) to integral using current direction'. No heraldic or cultural iconography.

Accounts I
Birth in Berkeley: rint as BSD and IEEE 754 binding4.3BSD math library (1986), Sun FDLIBM s_rint.c (1993), IEEE Std 754-1985

1983-1993

Before ISO C knew rint, William Kahan and colleagues designing IEEE 754 needed a language hook for the standard's roundToIntegral operation that respected rounding modes and signaled inexact. Berkeley's 4.3BSD libm introduced rint(double) alongside copysign, finite, and ieee_flags. Sun Microsystems' FDLIBM, written by K.C. Ng at SunPro, provided a portable, correctly-rounded implementation using the 2^52 trick: add and subtract 2^52 to force rounding via hardware. This code became the ancestor of FreeBSD msun, OpenBSD libm, Julia OpenLibm, and musl's math. rint was thus de facto standard on every workstation that mattered before C99. Established rint semantics (current mode + inexact) years before standardization; created the reference implementation still copied today; made -lm linkage idiomatic.

Standardization in C99: filling the float/long double gapISO/IEC 9899:1999 §7.12.9.4, Rationale for International Standard — Programming Languages — C (2003), WG14 papers N462, N736

1995-1999

C89 had only double math (sin, floor, etc.), causing costly double promotions for float code. WG14's C9X charter added float and long double variants for all <math.h> functions, systematic f/l suffixes, plus <fenv.h> and <complex.h>. rint was adopted from POSIX/SVID into the standard with two new siblings: rintf and rintl. Crucially, WG14 split the BSD rint into two functions: rint (may raise inexact) and nearbyint (never raises), because interval arithmetic and careful numerical code needed both. The type-generic macro rint in <tgmath.h> was added to give C limited overloading. Made rint portable and required for conforming C99 implementations; forced vendors (Microsoft, Borland, embedded) to implement correct rounding-mode dependence; introduced the rint vs nearbyint distinction that still confuses developers.

Accounts II
POSIX alignment and the -lm splitThe Open Group Single UNIX Specification v2 (1997), SUSv3/POSIX.1-2001, POSIX.1-2017

1997-2018

POSIX adopted rint earlier than ISO C (XPG4.2, 1992) and required it in <math.h> with -lm. Under POSIX, mathematical functions were historically in a separate library libm, so linking required -lm. Linux man-pages project (man 3 rint) and The Open Group documented that rint() uses current rounding mode and may raise FE_INEXACT, and that applications should include <fenv.h> to control it. POSIX also standardized thread-safety and reentrancy notes, and clarified that rint does not set errno. The bundling question persisted: glibc 2.17+ merged libm into libc for convenience, but POSIX still documents -lm for portability. Ensured rint available on every POSIX system (Linux, *BSD, macOS, Solaris); cemented -lm folklore; made man 3 rint the de facto tutorial for C programmers.

The inexact wars: rint vs nearbyint in the wildglibc Bugzilla #6794, #13818; musl commit 0b4b6a7; LLVM libc implementation; cppreference revision history

2001-2023

The subtle 'may raise inexact' clause caused divergence. glibc 2.3's rint was implemented as nearbyint under the hood on x87, never raising FE_INEXACT, breaking code that used fetestexcept to detect rounding. Conversely, some embedded libms always raised even when not needed. WG14 defect report clarified intent: rint should raise if rounding occurred on IEC 60559 implementations, nearbyint must not. Fixes landed: glibc 2.5 corrected x87 assembly to use frndint vs. fsave, musl implemented rint via __rint_tmp with explicit inexact handling, and LLVM's correctly-rounded libm (2021) proved rint correctly rounded to <0.5 ulp with proper flag. The episode is cited in teaching as why two functions exist. Current major libms now correctly differentiate rint/nearbyint; textbooks and cppreference explicitly warn not to use rint when suppression of inexact is required; static analyzers flag misuse.

Modern afterlife: from C to C++ constexpr and SIMDISO/IEC 14882:2017 (C++17) <cmath> special functions; GCE-Math (2016), LLVM libm, SLEEF, Intel SVML documentation; CORE-MATH project (2022)

2011-2024

C++11 imported rint into std:: via <cmath> with overloads for float/double/long double and integral types, and made it potentially constexpr in C++23/C++26 proposals. Parallel worlds emerged: GCE-Math reimplemented rint as constexpr for compile-time calculation; vectorized libraries (SLEEF, Yeppp!, Agner Fog VCL, Intel SVML) provided SIMD rint for 4/8 doubles at once using hardware VRINT instructions (SSE4.1 roundsd, AVX-512). The CORE-MATH and RLIBM projects (2022-2024) delivered formally proven correctly-rounded rint for double and float, used to validate glibc and LLVM. Meanwhile C23 retained rint unchanged, confirming its permanence despite newer round/lround alternatives. rint remains the only standard rounding function that is both mode-sensitive and exception-signaling, ensuring continued relevance for rigorous numerics, even as most application code prefers round() for its mode-independence.

rint always rounds to the nearest integer, halfway to even, regardless of settings. — rint rounds using the current rounding direction from <fenv.h>. Only under the default FE_TONEAREST does it round to nearest even. Under FE_TOWARDZERO it truncates, under FE_UPWARD it ceils. Use round() if you need mode-independent nearest-away-from-zero.

rint and nearbyint are identical and interchangeable. — They differ in one normative requirement: rint may (and on IEC 60559 should) raise FE_INEXACT when rounding occurs; nearbyint is required never to raise FE_INEXACT. Code that tests fetestexcept(FE_INEXACT) to detect rounding must use rint.

rint converts its argument to an integer type (int/long). — rint returns a floating-point value that happens to be integral (e.g., 2.0). It does not convert type. For integer conversion with rounding-mode dependence use lrint()/llrint(); for mode-independent conversion use lround()/llround(). Casting (long)rint(x) is redundant and may overflow silently.

rint is available in C89 and does not need <fenv.h>. — rint is C99 (and POSIX.1-2001). C89 has no rint, no rintf/l, no <fenv.h>, and no <tgmath.h>. On strict C89 compilers, including <math.h> will not declare rint without extensions.

You need to link with -lm on all systems to use rint. — Historically true on POSIX (libm separate). Modern glibc (2.17+) merges libm into libc, and on macOS/BSD libm is part of libSystem; -lm is accepted for portability but often unnecessary. Still required on many embedded toolchains and when using -std=c99 -pedantic with explicit libm split.
