Who It Is

rint() does not simply round — it listens. Unlike its blunt cousins that always round halfway away from zero, rint() asks the floating-point environment how it should behave, and then may quietly raise a flag to say it had to do work at all.

Deterministic but context-sensitive. rint respects the dynamically set rounding direction (fesetround), making it the only classic rounding function that is not fixed-policy. Under default roundTiesToEven (banker's rounding), 1.5 → 2.0, 2.5 → 2.0, -1.5 → -2.0. Under FE_UPWARD, 1.5 → 2.0, -1.5 → -1.0. It returns a floating-point value (e.g., 2.0 not integer 2), preserving type and allowing large integral values beyond int range. Powers
Current-direction rounding to integral floating-point value

Rounds argument x to nearest integral value representable as floating-point, using current rounding direction set by fesetround(). Under default FE_TONEAREST, ties to even.

Limit: Result is still floating-point type, not integer type; may lose integer precision if x magnitude > 2^mantissa bits but still returns x unchanged. Does not convert to int; use lrint/llrint for that. Behavior undefined if FENV_ACCESS not enabled and compiler optimizes away mode changes.

Signaling inexact exception (FE_INEXACT)

If the rounded result differs from the argument, rint may raise the floating-point inexact exception (FE_INEXACT). This allows detection that rounding occurred.

Limit: Exception raising is observable only via fetestexcept(FE_INEXACT) after feclearexcept; many programs ignore fenv. nearbyint() is identical but guaranteed NOT to raise inexact — key distinction.

IEEE 754 special-value propagation

Preserves NaN payloads (returns NaN), returns ±Inf unchanged, returns ±0.0 unchanged with sign preserved. Does not signal invalid for infinities.

Limit: Signaling NaN may be quieted per implementation. No domain error; errno not set.

Type-generic dispatch and constexpr potential

Via <tgmath.h> macro rint(x) and C++ overloads, dispatches to float/double/long double and complex? (real only). In C++23 and GCE-Math, can be evaluated at compile time (constexpr) when using correctly rounded constexpr libm.

Limit: tgmath.h only for real types; complex variants not provided for rint. constexpr support non-standard before C++23/C23.

Hardware acceleration path

On x86, ARMv8, RISC-V, maps to single instruction (FRNDINT, VRNDSCALE, etc.) when rounding mode matches hardware, giving near-zero cost and correctly rounded result.

Limit: If hardware does not support dynamic rounding mode, libm must change control word, costing pipeline flush. Correctly rounded requirement (<0.5 ulp) holds per IEEE 754 but some fast-math modes (-ffast-math) may break it.

Accounts I
The C99 Birth: Filling the Rounding GapISO/IEC 9899:1999 Rationale, §7.12.9; WG14 papers N773, N774 (1998)

1995-1999

C89 offered only floor(), ceil(), fabs() and integer abs/div. Numerical programmers needed IEEE 754 rounding control. WG14, aligning C with IEEE 754-1985 and POSIX, introduced a family: rint, nearbyint, round, lrint, llrint, lround, llround. rint was the direct exposure of IEEE roundToIntegral with current direction. The Rationale notes rint existed in BSD 4.3 (1986) libm and was standardized to avoid divergence. Adoption required new headers <fenv.h> and <tgmath.h> to make rounding mode observable. C became viable for portable numerical code; libm vendors had to implement fenv correctly. rint became the canonical way to round without leaving floating-point domain.

BSD to Everywhere: Sun FDLIBM and the libm DiasporaSun Microsystems FDLIBM source comments (1993), FreeBSD msun history, OpenLibm README

1986-2005

Sun's Freely Distributable LIBM (FDLIBM) by K.C. Ng implemented rint via bit-manipulation and scaling to avoid hardware mode switches, ensuring correct rounding even without FRNDINT. FreeBSD's msun and OpenBSD's libm forked FDLIBM, preserving its rint.c. Julia's OpenLibm (2013) reused it. Musl (2011) rewrote rint from scratch in ~30 lines of portable C, prioritizing correctness over speed. LLVM's libm (2020) reimplemented with formal proof of correct rounding using RLIBM techniques. Demonstrated multiple correct implementations of same spec; allowed comparison of correctly rounded vs fast. Established rint as benchmark for libm quality.

The Twin That Doesn't Signal: rint vs nearbyintC99 §7.12.9.3 vs §7.12.9.4; POSIX rationale; glibc bugzilla #6792

1999-present

C99 introduced two nearly identical functions: rint (may raise FE_INEXACT) and nearbyint (shall not raise FE_INEXACT, per IEEE 754 nearbyint). The difference matters for numerical algorithms that use inexact flag to detect non-integral inputs, and for implementing interval arithmetic. Many textbooks incorrectly state they are identical. glibc initially implemented nearbyint as alias to rint, violating spec until bug report 6792 (2008) forced separate implementation using hardware flag suppression. Clarified that rint is for detection, nearbyint for silent rounding; affected correctness of math libraries that suppress exceptions.

Accounts II
Banker's Rounding in the Wild: When 2.5 Becomes 2.0IEEE 754-2008 §4.3.1; Python issue 5532; Stack Overflow questions 3952127, 10851273

2008-2020

Default FE_TONEAREST uses ties-to-even to reduce statistical bias. rint(2.5) → 2.0, rint(3.5) → 4.0. Developers expecting school rounding (half away from zero) are surprised when rint does not match round(). Python's round() in Python 3 switched to bankers rounding, explicitly citing C rint/IEEE 754. Countless Stack Overflow answers confuse rint with round, leading to financial bugs where $2.5 truncated to $2. Led to widespread misconception documentation; CERT and MISRA guidelines now warn to choose explicitly between rint and round for financial code.

Linker Lore: The -lm SeparationPOSIX.1-2001; GNU ld documentation; Linux man-pages project history

1971-2020

Historical Unix kept math functions in separate libm to save memory on small machines. rint, being part of libm, requires -lm on Linux/BSD. Newcomers compiling 'gcc foo.c -o foo' get undefined reference to rint. Modern glibc and musl still require explicit linking on some toolchains, while Windows and macOS link automatically. LLVM and GCC -ffast-math and -fno-math-errno affect whether rint is inlined or not. The separation is a living fossil of 1970s PDP-11 constraints. Perpetual beginner pitfall; build systems must conditionally add -lm. Recent GCC (2023) auto-links libm but POSIX still documents requirement.

Correctly Rounded Crusade: CRlibm, CORE-MATH and RLIBMCRlibm paper (Daramy et al., 2003); CORE-MATH project (Sibidanov et al., 2022); RLIBM paper PLDI 2021

2003-2024

Standard requires rint be correctly rounded (<0.5 ulp error), which is trivial for rounding but non-trivial to prove for software fallback. Arénaire's CRlibm proved correct rounding for rint via Coq. CORE-MATH (2022) re-proved all double-precision rint variants correctly rounded for all rounding modes. RLIBM (Rutgers) used exhaustive interval analysis to generate correctly rounded rintf for float. These projects use rint as test case for formal methods, contrasting with AMD libm and Intel libm which prioritize speed and are not formally verified. Established that even simple rint needs proof when emulated; influenced LLVM libm to adopt correctly rounded guarantee.

rint() is the same as round() or (int)(x+0.5) — rint respects current rounding mode (default ties-to-even) and returns floating-point, while round() always rounds halfway away from zero and is mode-independent. (int)(x+0.5) fails for negative numbers and large values. rint(2.5)=2.0 but round(2.5)=3.0 under default mode.

rint() returns an integer type (int/long) — rint returns floating-point (double/float/long double) with integral value (e.g., 2.0). To get integer type, use lrint() or llrint(), which also handle overflow via FE_INVALID.

rint() and nearbyint() are identical and interchangeable — They differ only in exception behavior: rint may raise FE_INEXACT, nearbyint never does. This matters for code that tests inexact flag to detect fractional input.

rint is obsolete or deprecated in favor of round — Both are current C17/C23. rint is preferred when you need IEEE 754 mode-sensitive rounding or want to detect inexact via floating-point environment; round is preferred for deterministic half-away behavior.

Calling rint does not require <fenv.h> or special pragma — rint works without <fenv.h>, but to observe or change its mode-sensitive behavior portably you must include <fenv.h> and enable #pragma STDC FENV_ACCESS ON; otherwise compiler may optimize away mode changes.
